As‑Is → To‑Be

専用ハードと、終わらないアノテーション。
その2つの壁を同時に外す。

導入コストの高い専用機材と、学習データを作り続ける運用コスト。どちらも「気軽に・誰でも」を阻んできた。スマホ再利用と生成AIで、両方を不要にする。

AS‑IS 現状の課題

  • 害獣対策・動物追跡に、高価で専用のトレイルカメラが必要 — 導入ハードルが高い。
  • YOLO等の物体検出は、継続的なアノテーション（学習データ作成）のコストと手間がかかる。

TO‑BE 実現したい姿

  • 不要になった古いAndroidスマホをエッジ端末として再利用。誰でも気軽に設置。
  • 画像をS3へ送り、クラウドの生成AIで検出・分類。アノテーション作業を完全に不要化。
  • 自然観察・自治体の害獣対策・学術研究まで幅広く寄与するプラットフォームへ。

Tech Stack

各レイヤの採用サービスと、その理由。

AWSのマネージドサービスを最大限活用。すべて Terraform でコード管理し、推論は生成AIに一本化する（Rekognition Custom Labels は「アノテーション不要」の方針と相反するため不採用）。

レイヤ採用サービス選定理由
モバイルAndroid / Kotlin + CameraX常時監視・端末内動体検知はOS制御が深いネイティブが最適。省電力・端末互換性に強い。
端末認証Cognito Identity Pool端末ごとに一時クレデンシャルを発行し、S3への直接アップロードを安全に実現。
ストレージAmazon S3マルチパートで不安定回線の再送に強い。不完全マルチパートの自動Abortルールは必須設定。
バッファAmazon SQS再接続バーストを吸収し、下流の推論呼び出しレートをならす。
オーケストレーションEventBridge Pipes + Step Functions (Express)一次分類→エスカレーションの分岐を宣言的に記述。スロットリングへのbackoffリトライを内蔵し可観測性が高い。
AI 推論Google Cloud Vertex AI (Gemini)アノテーション不要の中核。tool use / JSON Schema で構造化出力しDB投入を確実化。
データベースAmazon DynamoDB時系列追記中心のアクセスパターンに合致。GSIは時間軸ミックスでホットパーティション回避。
通知SNS + FCM / SES重要検出のファンアウト。将来の複数ユーザー・自治体宛て購読管理にトピックが効く。
API / 閲覧API Gateway HTTP API + S3/CloudFrontTerraform記述が軽くPoC向き。Amplify Gen2(=CDK)は不採用で一貫性を保つ。
IaC / 監視Terraform + CloudWatch全AWSリソースをコード管理。推論コスト・Lambda/SFnエラーを可観測化。
制御プレーン（本番）AWS IoT Core大規模フリートの遠隔設定・死活監視・遠隔コマンド。PoCでは導入せず成長フェーズで後付け。
Power · Heat · Doze

野外で数日〜数週間。
本当の壁は「熱と電源」。

CPU/カメラをフル稼働させれば、数時間でバッテリー枯渇かサーマルスロットリングでOSが落ちる。ソフトの工夫で無人稼働を伸ばす。

照度センサーで夜間スリープ

日没でルクスが閾値以下になればCameraXを完全unbind。真っ黒なノイズ画像を生成AIに送る無駄を根絶。ヒステリシスでチャタリング防止。

適応 Duty Cycle（Thermal API）

「3秒オン／27秒オフ」のような間欠動作。熱余裕の低下を検知したら自動でオフ時間延長・解像度低下し、強制終了を事前回避。

OEM 電池キラー対策

Xiaomi/Huawei/Oppo等の独自制限は標準設定だけでは不足。Autostart許可・最適化除外をオンボーディングで機種別に案内。
